## 배경

할 일 목록과 타이머는 공부 계획과 시간을 기록하기엔 충분하지만, 쌓인 기록이 눈에 보이는 보상으로 이어지지는 않습니다. 공부를 게임처럼 만들면 더 재미있게, 더 꾸준히 할 수 있겠다고 생각해 게이미피케이션을 택했습니다. 배경을 우주로 고른 것은 다음 목적지로 한 칸씩 나아가는 탐험 방식이 매일 조금씩 쌓이는 공부와 맞는다고 봤기 때문입니다.

**우주공부선(Space Study Ship)** 은 공부한 시간을 연료로 바꾸고, 그 연료로 행성과 지역을 해금하며 우주를 탐험하게 만든 학습 관리 앱입니다. 타이머로 30분을 공부하면 연료 1이 쌓이고, 누적 학습 시간이나 연속 학습일 같은 목표를 채우면 배지를 받습니다.

2026년 1학기 창의학기제 과제(학생들의 학습 지속성 향상을 위한 게이미피케이션 기반 Todo + Timer 서비스 개발)로 진행한 1인 과제였습니다. 한 학기 안에 화면뿐 아니라 공부 시간 계산, 보상 지급, 데이터 저장이 한 서비스 안에서 맞물려 돌아가게 만들어야 했습니다. 서버의 초기 멀티모듈 구조와 배포 설정은 다른 기여자가 잡아 두었습니다.

## 맡은 역할

- **Flutter 앱 전체** — 할 일·카테고리, 타이머, 연료, 탐험, 배지, 게스트 모드와 로그인 화면
- **서버 도메인 기능** — Spring Boot·PostgreSQL 서버의 할 일·카테고리, 연료, 타이머 세션, 오늘 통계, 탐험 기능
- **서버 인증 기능** — Google·Apple 로그인의 Firebase ID 토큰 검증, 기기별 세션·FCM 토큰 저장, 닉네임 변경, 회원 탈퇴
- **기획과 보고** — 매주 개발 순서와 학습 목표를 정하고 주간 보고서·최종 발표로 정리

## 과정

**로그인 없이 도는 앱부터 만들었습니다.** 1~5주차에는 타이머, 할 일, 연료·탐험·배지를 서버 없이 기기 안에서 동작하게 만들었습니다. 6주차 휴강 뒤 7~10주차에 서버와 로그인을 구축했고, 11~12주차에 학습 기록, 연료, 탐험 데이터를 서버와 연결했습니다. 덕분에 회원가입 없이 쓰는 게스트 모드와 로그인 후 서버에 저장하는 방식을 함께 지원하게 됐습니다.

**앱에서 먼저 정한 규칙을 서버가 따라갔습니다.** 서버에 연료 기능을 붙일 때, 게스트 모드에서 이미 쓰고 있던 "30분에 연료 1, 남은 분은 다음으로 이월" 규칙을 서버도 그대로 따르게 했습니다.

**서버 연결 단계에서 시간을 가장 많이 쓴 건 정합성이었습니다.** 통신이 끊겨 같은 기록이 다시 전송되면 연료가 두 번 지급될 수 있었고, 기록 저장과 연료 충전 중 하나만 성공하면 공부 기록과 보상이 어긋났습니다. 이 두 문제를 막는 구조를 타이머·연료·탐험 기능에 차례로 넣었습니다.

**같은 오류를 세 번 만났습니다.** 로그아웃과 게스트 전환 과정에서 인증 관리 코드와 저장소가 서로를 참조해 Riverpod 순환 의존성 오류가 났습니다. 처음 두 번은 할 일 캐시, 연료 캐시처럼 문제가 난 곳만 데이터 소스를 직접 읽도록 고쳤습니다. 세 번째에 호출 관계를 따라가 보고, 로그아웃·게스트 전환 전체에서 인증 관리 코드가 데이터 접근 계층을 바로 호출하도록 정리하고 수동 캐시 무효화를 없앴습니다.

**구현하며 생긴 문제는 다음 주 과제로 넘겼습니다.** 매주 개발 순서와 학습 목표를 정하고, 그 주에 해결하지 못한 문제는 다음 주 계획에 넣어 이어서 풀었습니다.

## 기술적 결정

### 공부를 우주 탐험 게임으로

- **상황**: 기존 Todo·타이머 앱은 기록에 그쳐, 꾸준히 쓸 동기와 누적된 노력에 대한 눈에 보이는 성취감이 약했습니다(기획서의 문제 정의).
- **문제**: 공부한 시간이 숫자 기록으로만 남으면 공부를 이어 갈 이유가 되지 못합니다.
- **결정**: 공부 시간 → 연료 → 탐험으로 이어지는 구조를 만들었습니다. 타이머 30분마다 연료 1을 주고 남은 분은 다음으로 이월하며, 연료로 행성과 지역을 해금하고, 누적 학습 시간·연속 학습일 목표를 채우면 배지를 줍니다.

### 저장 요청마다 식별키를 붙여 중복 지급 방지

- **상황**: 모바일 앱은 통신이 끊기면 같은 공부 기록을 다시 보낼 수 있습니다.
- **문제**: 같은 기록이 두 번 저장되면 연료도 두 번 지급됩니다.
- **결정**: 타이머 기록 저장 요청에 `Idempotency-Key`를 붙여, 이미 처리한 키로 다시 오면 기존 결과만 돌려주게 했습니다. 연료 쪽에도 거래 ID로 중복을 한 번 더 막고, 같은 키가 동시에 들어오는 경우는 유니크 제약 위반을 잡아 다시 조회하게 했습니다.

### 기록 저장·연료 충전·학습시간 반영을 하나의 트랜잭션으로

- **상황**: 공부 기록 하나가 저장되면 연료 충전과 할 일의 학습시간 반영이 함께 일어나야 합니다.
- **결정**: 세 작업을 하나의 트랜잭션으로 묶어 중간에 실패하면 모두 취소되게 했습니다. 행성·지역 해금도 연료 차감과 함께 처리했습니다.

### 기기별 세션 관리를 위해 Refresh Token을 DB로 이동

- **상황**: 기존 서버는 Refresh Token을 Redis에 회원당 하나만 저장해, 회원당 한 기기의 세션만 유효했습니다.
- **결정**: API 스펙이 기기별 관리를 전제했기 때문에 Refresh Token을 기기 테이블(`user_devices`)에 함께 저장하고, 토큰 안에 기기 ID를 넣어 로그아웃·재발급 시 기기를 구분하게 했습니다. 같은 기기를 다른 계정이 쓰는 경우는 (회원, 기기) 조합으로 구분했습니다.
- **결과**: 배포 직후 기존 사용자는 한 번 강제 로그아웃되는데, 설계 단계에서 의도한 결과로 받아들였습니다.

## 결과

- 학기 말 기준 앱과 서버가 연동된 베타 버전 완성, 최종 발표 당시 Google Play 비공개 테스트 버전 게시
- 탐험 콘텐츠 행성 8개·세부 지역 30개, 배지 6개 범주 25개(획득 상태는 기기에 저장)
- 서버 API 23개(인증 6, 할 일·카테고리 8, 타이머 3, 연료 2, 탐험 4)
- 학기 중 보고서 기준 프론트엔드·백엔드 자동 테스트 240개 이상 통과
- 소셜 화면은 샘플 데이터로 구성돼 있으며, 소셜과 배지의 서버 연동은 남은 과제입니다
