## 배경

**Stocker**는 주식 투자를 처음 시작하는 사람을 위한 금융 교육 앱입니다. 챕터별 이론 학습, O/X 퀴즈와 해설, 틀린 문제를 모으는 오답노트, 캘린더 출석 체크, 20개 문항으로 5가지 투자자 유형을 분류하는 투자 성향 분석, 학습 노트를 한 앱에서 제공합니다.

팀 **돔황촤 코스피**로 진행했고, 저는 앱 프론트엔드 리드를 맡았습니다. Flutter로 iOS와 Android를 함께 개발했고, 백엔드는 Node.js REST API(JWT 인증)입니다. Flutter 앱은 팀원과 브랜치를 나눠 개발한 뒤 하나로 합쳤습니다.

## 맡은 역할

- **앱 프론트엔드 리드** — Flutter 앱의 구조, 브랜치 통합, 상태관리 전환을 주도
- **앱 구조 설계** — 저장소 최초 구성, 기능별 `data / domain / presentation` 구조와 상태관리·라우팅 뼈대
- **학습 기능 화면** — 이론 학습, 퀴즈, 오답노트, 마이페이지, 다크/라이트 테마
- **브랜치 통합** — 팀원 브랜치(회원가입·로그인, 투자 성향 분석, 노트, 출석 퀴즈)와 내 브랜치를 하나의 앱으로 통합
- **상태관리 전환** — Provider에서 Riverpod으로 단계적 마이그레이션
- **실서버 연동과 마감** — API 통신 로깅, 퀴즈 API 호출 축소, 인증 가드 라우팅, 서버 에러 메시지 통합, 퀴즈 중간 이탈 방지, 로그인 후 투자 성향 분석 유도, 스플래시, Android 릴리스 빌드 수정

## 과정

**백엔드보다 먼저 화면을 만들었습니다.** 2025년 7월 26일 저장소를 구성한 뒤, 이론 학습 화면을 Mock 데이터로 먼저 만들고 API 요청·응답 DTO와 Repository를 붙여 실제 API로 바꿀 수 있는 구조를 잡았습니다.

**두 갈래로 개발한 기능을 하나로 합쳤습니다.** 8월 26일 제 브랜치(테마, 퀴즈, 이론, 오답노트, 마이페이지)를 기준으로 팀원 브랜치(노트, 투자 성향 분석, 출석, 네트워크·인증)를 통합했습니다. 통합 직후 홈 화면의 `dispose()`에서 Provider를 읽다가 이미 비활성화된 위젯 트리에 접근하는 오류가 났고, Provider 참조를 미리 저장해두는 방식으로 고쳤습니다.

**실서버에 붙이자 새로운 문제가 나왔습니다.** 9월에는 통신, 인증, 퀴즈, 완료 여부 필드, 무한 루프, 오답노트를 차례로 고쳤습니다. 11월에는 API 요청·응답을 콘솔에 그대로 찍는 로깅 시스템을 먼저 만들고, 같은 날 API 필드명과 라우팅을 수정했습니다.

**퀴즈 API 호출을 시작과 끝, 두 번으로 줄였습니다.** 퀴즈는 답을 고를 때마다 서버를 호출하고 있었습니다. 11월 21일 듀오링고 방식을 참고해, 시작할 때 문제를 한 번에 받아두고 답안은 기기에 저장했다가 끝날 때 한 번에 제출하도록 바꿨습니다.

**마지막 버그는 릴리스 빌드에서 나왔습니다.** 11월 28일, 릴리스 APK에서만 네트워크 요청이 막히는 문제를 찾았습니다. main `AndroidManifest.xml`에 INTERNET 권한이 빠져 있었고, 같은 커밋에서 15초여야 할 Dio 타임아웃이 15000초로 계산되던 버그도 고쳤습니다.

## 기술적 결정

### Mock 우선 개발과 실행 설정으로 Mock·Real 전환

- **상황**: 백엔드 API가 완성되기 전에도 화면 개발을 진행해야 했습니다. 팀 개발 가이드에 "개발 시 Mock 데이터 사용"을 원칙으로 두었습니다.
- **결정**: 데이터 소스를 Repository 뒤로 숨기고 Mock과 Real 구현을 나눴습니다. 처음에는 `main.dart`의 `useMock` 상수를 직접 바꿔 전환했지만, 11월에 `--dart-define` 값과 VS Code 실행 설정(Mock / Mock + 테스트 유저 / Real)으로 바꿨습니다.
- **결과**: 코드를 수정하지 않고 실행 환경을 전환할 수 있게 되었고, 잘못된 설정을 실수로 커밋할 위험이 없어졌습니다.

### Provider에서 Riverpod으로 단계적 전환

- **상황**: 처음 팀 가이드는 "상태 관리는 Provider만 사용"이었습니다.
- **문제**: Provider는 BuildContext가 있어야 접근할 수 있고, 등록되지 않은 Provider는 실행해봐야 에러가 나며, Provider끼리 참조하려면 ProxyProvider가 필요했습니다.
- **결정**: 한 번에 바꾸지 않고 단계로 나눴습니다. Phase 0에서 기존 Provider 패키지에 `legacy_provider` 접두어를 붙여 Riverpod과 공존시키고, 테마·내비게이션 → Repository → 인증·출석·노트·교육·퀴즈·오답노트·성향분석 Notifier → UI 순서로 옮긴 뒤 Provider 패키지를 제거했습니다.
- **결과**: 2025년 11월 8일 Provider 의존성을 완전히 제거했습니다.

### 인증 가드와 서버 에러 메시지 통합

- **상황**: 로그인하지 않아도 홈(`/education`)을 비롯한 모든 화면에 접근할 수 있었습니다.
- **결정**: GoRouter `redirect`로 미인증 사용자를 `/login?redirect=원래경로`로 보내고, 로그인하면 원래 화면으로 돌아오게 했습니다. DioException에서 서버의 `message` 필드를 꺼내는 유틸리티를 만들어 인증·교육·퀴즈·출석 Notifier에 적용했습니다.

### 퀴즈 API 호출을 시작·종료 두 번으로 축소

- **상황**: 퀴즈를 시작할 때(`POST /api/quiz/enter`)와 끝낼 때(`POST /api/quiz/complete`) 말고도 답을 고를 때마다 API를 호출했습니다. 처음 구현(8월)에서는 답안 제출(`POST /api/quiz/submit-answer`), 실서버 연동 후(9월)에는 진도 저장(`PATCH /api/quiz/progress`)이었습니다. N문제 퀴즈를 한 번 풀면 N + 2회를 호출했습니다.
- **문제**: 문제 수만큼 호출이 늘어 서버 부하가 커지고, 답을 고를 때마다 응답을 기다려야 했습니다.
- **결정**: 듀오링고의 방식을 참고했습니다. 시작할 때 `enter` 응답으로 문제와 정답·해설을 한 번에 받아두고, 답을 고르면 기기에만 저장한 뒤 정답 여부와 해설을 바로 보여줍니다. 채점은 마지막에 전체 답안을 `complete`로 한 번에 보내 서버에서 처리합니다.
- **결과**: 퀴즈 1회당 API 호출이 "문항 수 + 2"회에서 시작·종료 2회로 줄었습니다. 문항이 많을수록 줄어드는 비율이 커지는 구조입니다.

### 퀴즈는 시험 형식으로, 중간 이탈은 경고

- **문제**: 일반 퀴즈를 풀다 중간에 나가면 진행 상황이 사라졌습니다.
- **결정**: 시작 전 문제 수와 예상 소요 시간, 이탈 시 처음부터 다시 풀어야 한다는 안내를 띄우고, `PopScope`로 뒤로가기를 막아 "계속 풀기 / 나가기"를 고르게 했습니다. 오답노트의 단일 문제 풀이와 복습 모드에는 경고를 걸지 않았습니다.
