## 배경

여러 교회가 함께 쓰는 교회 홈페이지 서비스입니다. 교인은 설교·주보·소식을 보고, 성경 통독 챌린지와 차량 탑승 신청을 할 수 있습니다. 관리자는 콘텐츠와 회원, 역할·권한을 화면에서 직접 관리합니다.

처음부터 **다른 교회에도 다시 쓸 수 있는 템플릿**으로 설계했고, 새 교회를 받을 때 코드를 고치지 않는 "코드 수정 0"을 원칙으로 삼았습니다. 2026년 6월부터 백엔드와 프론트엔드를 혼자 만들었습니다.

## 함께 쓰는 교회

- **은샘교회** — 충청남도 예산군. 첫 교회이고 2026년 6월부터 `www.eunsaem.com`으로 운영 중입니다.
- **새누리교회** — 경기도 용인시 기흥구. 두 번째 교회이고 2026년 11월에 `www.snrbtc.com`으로 열었습니다.

백엔드는 하나이고, 교회마다 홈페이지(프론트엔드)만 따로 둡니다. 화면 자료는 은샘교회가 먼저, 새누리교회가 뒤에 나옵니다.

## 맡은 역할

- **백엔드 설계·구현** — Spring Boot 4·Java 21·PostgreSQL·Redis, JWT 인증과 RBAC
- **프론트엔드 구현** — Next.js 16 App Router·TypeScript, 공개·회원·관리자 화면
- **디자인 시스템** — 디자인 토큰과 공통 컴포넌트, 고령 교인을 위한 큰 글자·UI
- **배포·운영** — 백엔드 OCI VM, 프론트엔드 Vercel, GitHub Actions CI/CD
- **문서화** — 설계 명세, 새 교회 등록 가이드, 운영 전환 절차서, AI 에이전트용 `AGENTS.md`

## 과정

**기능을 이슈 단위로 쪼개고, 설계 문서부터 썼습니다.** 백엔드는 기반 4개와 도메인 13개로 나눴습니다. 기능마다 설계, 구현 계획, 구현, 코드리뷰 반영 순서로 PR을 만들어 6월 4일부터 7일까지 올렸습니다.

**연혁 페이지는 설계만 네 번 했습니다.** 풀스크린 히어로를 넣었다가 "모든 시대를 똑같이 다룬다"는 기준으로 걷어 냈습니다. 마지막에는 참고 사이트를 스크롤하며 관찰해 풀폭 그리드로 바꾸고, 스크롤 엔진을 지워 코드를 줄였습니다.

**실제 서버에 올리자 로컬에서는 안 보이던 문제가 나왔습니다.** 백엔드가 멈추면 홈 전체가 에러 페이지가 되어, 소식 영역만 실패하도록 격리했습니다. 상세 페이지가 전부 500을 낸 날은 jsdom이 이전 Node 런타임에서 돌지 않는 것이 원인이라 Node 22로 고정했습니다.

**기본 기능을 갖춘 뒤에도 기능을 이어서 붙였습니다.** 성경 66권 1,189장 구조로 읽음 기록을 계산하는 통독 챌린지, 위치 좌표를 첨부하는 차량 탑승 신청, PWA, 검색엔진 최적화를 넣었습니다.

**두 번째 교회는 템플릿을 복사해 만들었습니다.** 은샘교회 프론트엔드에서 교회 고유값을 걷어 낸 템플릿 레포를 만들고, 새누리교회는 그 템플릿에서 시작했습니다. 교회마다 바뀌는 것은 상수 파일, 사진, API 주소뿐입니다. 새누리교회에서는 네이비 브랜드 색과 로고, 사진으로 교회 역사를 넘겨 보는 홈 화면, 부서를 색깔 이름으로 부르는 여섯 미션팀 페이지를 새로 만들었습니다. 설교·공지·주보 목록은 월별로 정리하고, 마이페이지 관리 화면은 왼쪽 메뉴 구성으로 바꿨습니다.

**새누리교회를 만드는 도중에 서버 구조를 바꿨습니다.** 처음에는 새누리교회 레포에도 자체 서버 폴더와 서버 배포 워크플로가 있었습니다. 백엔드를 공용으로 전환한 뒤 이 둘을 지우고, 공용 서버에 교회를 등록한 다음 API 주소만 바꿔 연결했습니다.

## 기술적 결정

### 교회마다 별도 인스턴스에서 멀티테넌시로

- **처음 결정**: 테넌트 컬럼 없이 교회마다 DB와 배포 인스턴스를 따로 두어, 데이터 격리를 인프라에 맡겼습니다.
- **문제**: 운영 서버는 메모리가 1GB인데 앱 하나가 이미 58%를 쓰고 있었습니다. 교회를 30~40곳 받을 계획인데 교회마다 앱(약 350MB)을 띄울 수 없었고, 운영자가 한 명이라 교회 수만큼 서버를 늘리고 업데이트를 반복하기도 어려웠습니다.
- **근거**: 결정 전에 공식 문서로 찬반 근거를 먼저 정리했습니다.
  - [AWS SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/pool-isolation.html)는 고객마다 환경을 따로 두는 Silo와 전부 공유하는 Pool을 나누고, Silo는 격리가 가장 강한 대신 SaaS의 비용 효율을 대부분 얻지 못한다고 설명합니다. 방문자가 적은 교회 사이트를 Silo로 두면 자원 대부분이 놀게 됩니다.
  - [Microsoft Azure 아키텍처 가이드](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)는 고객이 많아질 것으로 예상되면 공유 인프라가 중요하고, 그렇지 않으면 늘어나는 인스턴스 무리를 관리해야 한다고 말합니다.
  - 같은 가이드는 반대 근거도 듭니다. 공유 구조는 한 곳의 문제가 모든 고객의 장애가 되고, 격리가 애플리케이션 코드의 책임이 됩니다. 고객이 소수라면 전용 자원이 낫다고도 합니다. 교회가 두세 곳에서 끝날 계획이었다면 바꾸지 않았을 것입니다.
- **결정**: 앱·DB·Redis를 하나로 두고 19개 테이블에 `church_id`를 넣어 Hibernate의 테넌트 기능으로 격리했습니다. 교회는 API 경로 앞부분(`/church/{교회키}`)으로 구분하고, 교회가 정해지지 않은 DB 접근은 예외로 막았습니다. 로그인 토큰에도 교회 식별자를 넣어 다른 교회 주소에서는 쓸 수 없게 했습니다.
- **전환**: 운영 중인 은샘교회 데이터(회원 30명, 업로드 파일 114개)를 잃지 않는 것이 조건이었습니다. 운영 DB 덤프로 새 버전 적용, 이전 버전으로 되돌리기, 다시 올리기를 로컬에서 먼저 연습한 뒤 전환했습니다. 옛 주소도 한동안 그대로 받게 해 백엔드와 프론트엔드를 따로 배포했습니다.
- **기각한 대안**: 앱만 공유하고 DB 스키마를 교회별로 나누는 중간 방식(Bridge)은 격리가 더 강하고 교회 하나만 복구하기도 쉽습니다. 하지만 테이블을 바꿀 때마다 30~40개 스키마에 각각 적용해야 하고, 새 교회 등록에 스키마 생성이 따라붙고, 백업도 교회 수만큼 늘어납니다. 운영자가 한 명이고 법적으로 물리적 분리가 요구되는 데이터가 아니어서, 관리할 것이 가장 적은 완전 공유 방식을 골랐습니다.
- **단점 대비**: 공동 장애는 매일 암호화 백업과 배포 때의 헬스 체크로, 코드 책임은 교회 간 격리 테스트로 대비했습니다. 네이티브 쿼리에 교회 조건이 빠지면 실패하는 테스트도 두었습니다.
- **결과**: 새 교회는 서버에서 스크립트를 한 번 실행하면 등록되고, 코드 수정과 재배포가 없습니다. 두 번째 교회인 새누리교회를 이 방식으로 추가했습니다.

### 직분과 권한을 분리한 RBAC

- **상황**: 교회의 목사·장로·교사 같은 직분이 곧 사이트 권한은 아닙니다.
- **결정**: 직분과 권한을 별개 축으로 두고, 인가는 항상 `SERMON_WRITE` 같은 권한 단위로 검사합니다.
- **문제**: 처음에는 관리자가 다른 관리자를 임명하고 강등할 수 있었습니다.
- **결과**: 역할 부여·회수는 자기보다 엄격히 낮은 역할만 가능하게 바꿨습니다.

### 등록·수정 폼은 모달 대신 전용 페이지로

- **상황**: 공지·설교는 전용 페이지에서, 일정·갤러리·주보는 모달에서 등록·수정했습니다.
- **문제**: 모바일에서 태그 선택창이 모달 뒤에 깔리는 등 모달 문제가 반복됐습니다.
- **결정**: 모든 도메인을 전용 페이지 폼으로 통일하고, 삭제 확인 같은 작은 대화상자만 모달로 남겼습니다.
- **대안**: 모바일에서만 모달을 전체 화면으로 키우는 안은 비용은 가장 적지만, 같은 계열의 문제가 남아 기각했습니다.

## 결과

- 은샘교회 홈페이지를 `www.eunsaem.com` 도메인으로 배포했습니다.
- 새누리교회 홈페이지를 `www.snrbtc.com` 도메인으로 배포하고 구글·네이버 사이트 소유 확인을 적용했습니다.
- 백엔드 하나가 은샘교회와 새누리교회를 함께 서비스합니다. 전환 과정에서 회원과 업로드 파일은 하나도 잃지 않았습니다.
- 교회 간 데이터 격리를 전용 테스트로 검증하고, DB와 업로드 파일을 매일 암호화해 백업합니다.
- 설교·공지·일정·주보·갤러리, 성경 통독 챌린지, 차량 탑승 신청, 관리자 기능, PWA 설치를 지원합니다.
- 사이트맵·RSS·구조화 데이터를 갖추고 네이버 사이트 소유 확인을 적용했습니다.
- 부서 사진을 WebP로 변환·리사이즈해 46MB에서 5.5MB로 줄였습니다.
- 백엔드는 PR마다 실제 PostgreSQL로 전체 테스트를 돌리고, `deploy` 브랜치에 올리면 자동으로 배포됩니다.

## 배운 점

- **처음 결정이 맞았던 조건이 바뀌면 결정도 바꿔야 합니다.** 교회 한 곳일 때는 인스턴스 분리가 가장 단순했지만, 30곳을 한 명이 운영한다는 조건에서는 서버 하나를 공유하는 쪽이 유일하게 가능한 구조였습니다.
- **증상을 하나씩 막기보다 문제가 생기는 구조를 없애는 편이 낫습니다.** 폼을 페이지로 옮기자 같은 계열의 모바일 문제가 함께 사라졌습니다.
- **배포가 서버에 손으로 남긴 상태에 기대면, 그 상태가 사라지는 날 깨집니다.** 서버의 레지스트리 토큰이 지워져 배포가 실패했고, 이후 배포마다 일회용 토큰을 쓰게 바꿨습니다.
