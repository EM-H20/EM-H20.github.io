## 배경

은샘침례교회의 홈페이지와 API 서버입니다. 교회 소식과 설교 영상, 주보, 사진을 한곳에서 볼 수 있고, 교회 회원 전용 콘텐츠와 관리자 기능을 갖추고 있습니다.

프론트엔드는 Next.js App Router와 TypeScript, Tailwind CSS, shadcn/ui로, 백엔드는 FastAPI와 SQLAlchemy로 만들었고 인증은 Supabase JWT를 씁니다. 2025년 7월 말부터 8월 사이에 다른 기여자 한 명이 백엔드 기본 코드와 리팩터링을 남겼고, 그 이후의 개발과 배포, 운영은 혼자 맡았습니다.

## 맡은 역할

- **프론트엔드** — 홈, 설교, 공지사항, 행사, 주보, 사진 갤러리, 문의, 회원가입·로그인 화면
- **백엔드 API** — FastAPI 라우터, 파일 업로드와 서버 측 썸네일 생성, 관리자·교회 회원·일반 회원 3단계 권한
- **관리자 기능** — 회원 가입 승인과 권한 변경, 설교·행사·공지 등록·수정·삭제
- **배포와 운영** — Docker Compose와 Nginx 리버스 프록시, Vercel, GitHub Actions CI, Google Search Console·네이버 Search Advisor 색인 설정
- **문서화** — 아키텍처, 폴더 구조, 코딩 컨벤션 문서를 `docs/`에 정리

## 과정

**정적 페이지에서 시작해 기능을 하나씩 붙였습니다.** 8월 초에는 히어로, 설교, 사역 소개 같은 정적 섹션을 만들었고, 중순부터 Supabase 인증, 3단계 역할, 관리자 대시보드, 행사·공지 기능을 차례로 올렸습니다.

**프로덕션 배포에 이틀을 씨름했습니다.** 9월 4일부터 5일까지 "빌드 1"부터 "배포 20"까지 이름 붙인 수정 커밋을 이어 가며 Vercel 설정, 잘못 만들어지는 API 주소, 중복된 `/api` 경로 문제를 하나씩 고쳤습니다. 마침내 프로덕션 배포에 성공했을 때 남긴 커밋 메시지는 "278전 1승 277패"였습니다.

**HTTPS 환경에서는 또 다른 문제가 나왔습니다.** 설교 페이지에서 Mixed Content 오류가 발생했습니다. API 기본 주소의 대체값이 `http://localhost`였던 것이 원인이었고, 프로덕션에서는 항상 같은 출처의 `/api`로 요청하도록 바꿔 해결했습니다.

**자동 로그아웃은 결국 지우고 다시 만들었습니다.** 로그인 세션 만료 기능을 넣은 뒤 무한 루프, 타이머가 실시간으로 줄지 않는 문제가 이어졌습니다. 비교용 타이머를 나란히 띄우는 디버깅 화면까지 만들어 보다가, 자동 로그아웃 관련 코드 약 1,600줄을 한 번에 삭제했습니다. 이후 30분 세션 타이머와 만료 5분 전 경고만 남긴 단순한 구조로 다시 구현했습니다.

**파일 관리도 한 번 초기화했습니다.** 갤러리 업로드가 실패하면 파일만 남는 고아 파일 문제가 있어, 파일을 먼저 지우고 DB를 나중에 지우는 2단계 삭제와 롤백을 넣었습니다. 이후에는 파일 삭제 기능을 모두 걷어 낸 깨끗한 상태로 되돌린 뒤, 기존 파일과 새 파일을 함께 다루는 컴포넌트 하나를 만들어 행사·갤러리·공지·주보 폼의 중복 로직을 없앴습니다.

**운영을 시작한 뒤에도 계속 고쳐 왔습니다.** 검색 엔진 색인 오류를 바로잡고, 예배 명칭과 시간 안내를 수정하고, 설교 목록에 페이지네이션을 넣었습니다. 이후 React·Next.js 보안 패치와 PWA 지원, Next.js 16 업그레이드까지 이어 갔습니다.

## 기술적 결정

### 프로덕션 API는 항상 같은 출처의 `/api`로

- **상황**: 프론트엔드는 Vercel에서 HTTPS로 서비스되고, 백엔드는 별도 서버에서 Docker로 운영됩니다.
- **문제**: API 주소 대체값이 `http://localhost`라 HTTPS 페이지에서 Mixed Content 오류가 났습니다.
- **결정**: 개발 환경에서만 환경 변수나 localhost를 쓰고, 프로덕션에서는 항상 `/api`로 요청하게 했습니다. `/api` 요청은 Vercel rewrites로 백엔드에 전달되고, 백엔드 앞단에서는 Nginx가 HTTPS 리버스 프록시를 맡습니다.

### 백엔드 CI를 Docker 기반으로 전환

- **상황**: CI에서 호스트의 Python으로 백엔드를 직접 실행했습니다.
- **문제**: 상대 임포트 에러가 나고, 로컬·서버(Docker)와 CI 환경이 달랐습니다.
- **결정**: CI에서도 Docker Compose로 운영 환경과 같은 컨테이너를 띄우고, 컨테이너 안에서 헬스체크와 API 엔드포인트 연결을 테스트하게 했습니다.
- **결과**: Python 버전 매트릭스가 필요 없어졌고, 실패하면 컨테이너 로그를 수집해 원인을 볼 수 있게 됐습니다.

### 행사 카테고리는 백엔드 모델 대신 프론트엔드 상수로

- **상황**: 행사 카테고리를 백엔드의 별도 모델과 API로 관리했습니다.
- **문제**: 카테고리별 검색·필터링에서 500 에러가 났고, 백엔드의 `category_id` 필드가 프론트엔드와 맞지 않았습니다.
- **결정**: 백엔드의 카테고리 모델과 API를 없애고, 6개 카테고리를 프론트엔드 상수로 정의한 뒤 필드를 `category` 하나로 통일했습니다.

### 설교 영상은 썸네일을 먼저 보여 주기

- **상황**: 설교 페이지에는 YouTube 영상이 여러 개 들어갑니다.
- **결정**: 처음에는 YouTube 썸네일만 보여 주고, 클릭했을 때 iframe을 불러오게 했습니다. 서버 데이터 조회에는 React Query를 도입하고 staleTime을 5분으로 잡았습니다.

- **고치는 것보다 지우고 다시 만드는 편이 빠를 때가 있습니다.** 자동 로그아웃과 파일 삭제 기능 모두, 복잡해진 코드를 걷어 내고 단순한 구조로 다시 만든 쪽이 남았습니다.
