## 배경

경찰과 도둑을 좋아해 직접 모여 뛰던 사람들이 "이걸 앱으로 하면 더 재밌겠다"는 생각으로 시작한 프로젝트입니다. **경찰과 도둑**은 오프라인 술래잡기에 지도, 위치 공유, 실시간 게임 상태를 더한 Flutter 앱입니다. 경찰은 도둑을 찾아 QR로 체포하고, 도둑은 도망치거나 감옥에서 탈출하며 게임을 이어갑니다. 호스트가 지도 위에 플레이 구역과 감옥을 그리고, 정해진 주기마다 도둑의 위치가 공개되며, 한 방에 최대 150명까지 참여합니다.

팀은 Flutter 앱, Spring Boot 게임 서버, Next.js 공식 사이트를 각각의 저장소로 나눠 개발했고, 저는 로그인부터 방 만들기, 게임 진행, 채팅, 커뮤니티, 배포까지 Flutter 앱의 구조 설계와 대부분의 기능 구현을 맡았습니다. 실제로 밖에서 뛰는 게임이라 화면이 꺼져도 위치와 연결이 유지돼야 했고, iOS·Android 양쪽 스토어에 계속 배포할 수 있어야 했습니다.

## 맡은 역할

- **앱 구조 설계** — 기능별 Clean Architecture(data·domain·presentation), Riverpod 상태 관리, GoRouter 라우팅, Dio/Retrofit 네트워크 계층
- **로그인·약관** — Google·Apple 소셜 로그인, 닉네임 설정, 필수 약관 동의 흐름과 미동의 응답을 전역 Dio 인터셉터로 처리, 회원 탈퇴
- **방 만들기·참여** — 지도 위에 원형·폴리곤 플레이 구역과 감옥을 그리는 생성 흐름, QR·초대 링크 딥링크 참가, 중복 참가 시 진행 중인 방으로 복귀
- **게임 진행** — 실시간 지도와 위치 공개, QR 체포, 감옥 이탈 판정과 자동 탈옥, 게임 타이머, 앱 강제 종료 후 재진입 시 이동 경로 복원, 전체·개인 결과와 팀 MVP, 결과 이미지 저장
- **실시간 채팅** — STOMP 기반 팀 채팅, 읽지 않은 메시지 추적과 미리보기, 메시지 신고, 채팅 알림 설정
- **커뮤니티** — 모집글·댓글·스크랩, 모임 채팅방(고정 공지·방장 강퇴·게임 초대 전송), 알림함과 게시글·댓글별 알림 설정
- **알림·운영 도구** — FCM 푸시와 알림 탭 이동, 공지사항(카테고리 필터·언어별 조회), Remote Config 버전·점검 관리, Crashlytics, Analytics 퍼널 이벤트, AdMob 광고
- **다국어** — 한국어·영어·일본어 메시지 외부화와 로케일별 로고·스플래시
- **배포 자동화** — GitHub Actions와 Fastlane으로 iOS TestFlight·Android Play Store 배포 파이프라인 구성, PR CI에 자동 테스트 추가
- **백그라운드 위치·연결 유지** — iOS는 백그라운드 위치 모드를 켜고 플레이어가 멈춰 있어도 위치 추적이 끊기지 않게 설정, Android는 Foreground Service와 Wake Lock으로 게임 중 화면이 꺼져도 위치 전송과 연결 유지
- **잠금 화면 게임 현황** — iOS Live Activity와 Android 게임 진행 알림 구현, TestFlight 서명 설정까지 반영
- **UX 개선과 스토어 심사** — 사용자 피드백을 바탕으로 한 흐름 개선, 앱 연결 작업과 스토어 심사 제출
- **프로젝트 기록 관리** — 앱·서버·웹 세 저장소의 회의·이슈·설계 결정을 한 볼트(cops-and-robbers-brain)로 정리

## 과정

**첫 이슈는 기능이 아니라 배포였습니다.** 앱 저장소의 1번 이슈는 iOS TestFlight 배포 자동화였고, 이어서 Android 릴리스 서명과 Play Store 배포를 붙였습니다. 이후에도 Xcode·iOS SDK 버전 업그레이드, Ruby 버전, CocoaPods 충돌로 배포가 여러 차례 깨졌고, 그때마다 고치다가 결국 모든 워크플로우의 Fastlane 설치를 Bundler 방식으로 통일했습니다.

**튜토리얼은 노출 방식을 세 번 바꾼 끝에 지웠습니다.** 처음 쓰는 사용자를 위해 화면마다 코치마크 튜토리얼을 넣었고, 이후 "팀별로 1회", "팀과 무관하게 1회", "별도 페이지로 분리"로 노출 방식을 세 번 바꿨습니다. 그래도 "튜토리얼을 강제한다, 답답하다"는 피드백이 계속 쌓였습니다. 코드를 다시 보니 문제는 횟수가 아니라 구조였습니다. 건너뛰기 버튼이 없는 코치마크와 닫을 수 없는 안내 다이얼로그가 게임 시작 직전 대기방에서 연달아 떴습니다. 그래서 코치마크를 전부 걷어내고, 설치 후 한 번만 보는 온보딩으로 바꿨습니다.

**제가 넣은 배터리 설정 게이트를 직접 걷어냈습니다.** Android에서 게임 중 화면을 끄면 서버 연결이 끊기는 문제가 있었습니다. 처음에는 삼성 배터리 정책 문제로 보고, 배터리 최적화를 "제한 없음"으로 바꾸지 않으면 방 만들기·참여하기를 막는 게이트를 직접 넣었습니다. 약 3개월 뒤 이 게이트가 가장 큰 진입 장벽으로 올라왔습니다. 다시 분석해 보니 프로세스는 살아 있어도 CPU가 잠들어 하트비트가 멈춘 것이 원인이었고, 내비게이션·음악 앱과 같은 방식으로 해결한 뒤 게이트를 없앴습니다.

**잠금 화면에서도 게임이 보이게 했습니다.** 휴대폰을 주머니에 넣고 뛰는 게임이라, 앱을 열지 않아도 다음 위치 공개 시각과 도주 중인 도둑 수를 볼 수 있도록 iOS Live Activity와 Android 게임 진행 알림을 만들었습니다. iOS 확장 기능은 본 앱과 따로 서명돼야 해서 TestFlight 배포 설정도 함께 고쳤고, 이후 앱을 다시 실행했을 때 기존 표시를 이어받고 끝난 게임의 표시를 정리하는 수정을 이어서 배포했습니다.

## 기술적 결정

### 배터리 설정을 요구하는 대신 Foreground Service + Wake Lock

- **상황**: Android에서 게임 중 홈으로 나가거나 화면을 끄면 STOMP 하트비트가 끊겨 게임이 중단됐습니다.
- **문제**: 이를 기기 배터리 정책 문제로 보고 세운 "배터리 제한 없음" 강제 게이트가 약 3개월간 가장 큰 진입 장벽이 됐습니다. iOS는 추가 설정 없이 동작하는데 Android만 사용자에게 OS 설정 변경을 요구하고 있었습니다.
- **결정**: Foreground Service(location)는 프로세스를, `PARTIAL_WAKE_LOCK`은 CPU를 깨워 두는 서로 다른 축으로 보고 둘 다 적용했습니다. Wake Lock은 정상 종료, 태스크 스와이프, 4시간 타임아웃 세 경로로 반드시 해제되게 했습니다.
- **대안**: 기존 방식(Foreground Service만 유지하고 배터리 설정을 강제)은 Foreground Service만으로는 CPU가 깨어 있지 않아 근본 해결이 아니므로 버렸습니다.
- **결과**: 방 만들기·참여하기의 배터리 차단 다이얼로그가 사라지고, 게임 진입 조건은 위치 권한 하나만 남았습니다.

### 강제 코치마크 대신 설치 후 1회 온보딩

- **상황**: 노출 정책을 세 번 바꿔도 "튜토리얼을 강제한다"는 피드백이 반복됐습니다.
- **결정**: 코치마크 엔진과 관련 서비스·라우트·의존성을 모두 삭제하고, 스플래시 직후 한 번만 보는 온보딩을 만들었습니다. 로그아웃해도 다시 띄우지 않고, 마이페이지에서 "앱 소개 다시 보기"로만 다시 열 수 있게 했습니다.
- **대안**: 다른 코치마크 패키지(showcaseview)는 같은 순차 스포트라이트 방식이라 갈아타도 사용자 경험이 같아 제외했습니다. 계획했던 온보딩 패키지(introduction_screen)도 이미 프로젝트에 있던 `smooth_page_indicator`로 직접 구현하는 쪽으로 바꿔, 새 의존성을 늘리지 않았습니다.

### 초대는 링크 하나로 — 앱과 웹이 나눠 맡은 딥링크

- **상황**: 방에 들어오려면 초대 코드를 직접 입력하거나 앱 안의 QR 스캐너로 찍어야 했습니다. 대기방 QR에는 초대 코드가 JSON으로 들어 있어서, 휴대폰 기본 카메라로 찍으면 의미 없는 텍스트만 보였습니다. 딥링크가 유입과 전환을 높인다는 업계 사례들을 보고 초대 흐름을 링크 하나로 바꾸기로 했습니다.
- **문제**: 링크를 눌렀을 때 OS가 앱을 바로 열려면 도메인에 검증 파일이 있어야 하는데, 그 도메인은 웹 프론트엔드 팀원이 맡은 Next.js 저장소에 있었습니다. 게다가 메모·문자에서는 앱이 열려도 카카오톡·인스타그램 인앱 브라우저, QR 촬영, 주소창 입력에서는 OS가 링크를 가로채지 않아 설치된 앱 대신 스토어로 넘어갔습니다.
- **결정**: 앱과 웹이 맡을 부분을 나누고, 이슈 문서로 주고받으며 풀었습니다. 앱은 App Links·Universal Links와 iOS 커스텀 스킴을 `app_links` 하나로 받아, 로그인 전에 받은 초대는 보관했다가 로그인 후 처리하고, 이미 참가한 방이면 그 방으로 돌려보내게 했습니다. 웹 팀원에게는 검증 파일 배치, 폴백 페이지 레퍼런스 코드, 검증 절차를 담은 핸드오프 문서를 넘겼습니다. 인앱 브라우저 문제는 웹의 `/join` 페이지가 인앱 브라우저를 빠져나와 Android `intent://`, iOS 커스텀 스킴으로 앱을 깨우고 실패하면 스토어로 보내는 브릿지를 맡고, 앱은 커스텀 스킴 등록과 콜드 스타트 때 홈 화면에 갇히는 경합을 고쳤습니다. 마지막으로 대기방 QR도 같은 링크로 바꿔, 기본 카메라로 찍어도 바로 방에 들어오게 했습니다.
- **대안**: 설계 단계에서 두 가지 한계를 먼저 확인하고, 처음부터 OS 네이티브 딥링크(App Links·Universal Links)로 설계했습니다. Firebase Dynamic Links는 2025년 8월 서비스가 종료돼 쓸 수 없었고, GoRouter 내장 딥링크는 초대 코드를 방 ID로 바꾸는 API 조회를 라우팅 전에 끼워 넣을 수 없었습니다. 그래서 `app_links`로 링크를 받는 시점을 직접 잡았습니다.
- **결과**: 카카오톡으로 받은 링크나 카메라로 찍은 QR 하나로 방에 바로 들어오게 됐습니다. 딥링크·QR 전환을 마친 직후인 2026년 6월 18일 156명이던 사용자 수(탈퇴 제외)는 10월 12일 620명으로 약 4배가 됐습니다.

### 카드 탭 체포 대신 QR 대면 체포, 그리고 30초 만료

- **상황**: 처음에는 경찰이 참가자 목록에서 도둑의 카드를 눌러 체포했습니다.
- **문제**: 뛰면서 목록에서 닉네임을 찾기 어려웠고, 다른 사람을 잘못 누르는 오탐이 생겼고, 멀리서도 체포가 됐습니다. 서로 믿고 하는 아너 시스템에 맡겨 두었지만 믿을 만한 기준은 아니었습니다.
- **결정**: 도둑이 자기 QR을 띄우고 경찰이 카메라로 찍어야만 체포되게 바꿨습니다. 찍는 행위 자체가 두 사람이 같은 자리에 있다는 증거라 확인 모달도 없앴고, 카드 탭 체포는 디버그 빌드 전용으로 돌렸습니다. 백엔드 체포 API는 그대로 쓰고 앱 흐름만 바꿨습니다.
- **후속**: 그런데 QR에는 참가자 ID만 들어 있어서, 한 번 사진을 찍어 두면 그 사진으로 언제든 멀리서 체포할 수 있었습니다. 그래서 QR에 만료 시각을 넣어 30초가 지나면 경찰 쪽에서 거부하게 했습니다. QR 창을 열 때마다 새로 발급하고, 만료 시각이 없는 구버전 QR은 강제 업데이트를 전제로 받지 않았습니다.
- **대안**: 서버 검증이나 세션별 서명을 넣으면 위조 QR까지 막을 수 있지만 백엔드 변경이 필요합니다. 함께 뛰는 사람들끼리 하는 게임에서 앱을 뜯어 QR을 위조하는 것은 현실적인 위협이 아니라고 보고, 찍어 둔 QR 사진의 재사용을 막는 데까지만 적용했습니다.
- **결과**: 체포는 실제로 마주친 상태에서만 성립하고, 찍어 둔 QR 사진은 30초 뒤면 쓸 수 없습니다. 만료 경계(1ms 전·같은 시각·1ms 후)는 단위 테스트로 고정했습니다.

### REST는 조회·명령, STOMP는 실시간 이벤트

- **상황**: 체포·탈옥 같은 요청과 위치 공개·체포 알림 같은 이벤트가 한 게임 안에서 동시에 오갑니다.
- **결정**: 요청은 REST로 보내고, 이벤트는 STOMP로 받도록 나눴습니다.
- **결과**: 연결이 끊겼다 복구되면 REST 상태 스냅샷으로 놓친 상태를 보정합니다.

## 배운 점

- **사용자에게 설정 변경을 요구하기 전에, 같은 종류의 앱은 어떻게 동작하는지 먼저 확인해야 합니다.** 내비게이션·음악 앱은 배터리 설정을 요구하지 않는데, 저는 연결 끊김을 기기 정책 문제로 보고 게이트를 세웠습니다. 실제 원인은 CPU가 잠드는 것을 놓친 제 구현이었습니다.
- **같은 불만이 반복되면 노출 횟수가 아니라 구조를 봐야 합니다.** 튜토리얼을 언제, 몇 번 띄울지만 세 번 바꾸는 동안 건너뛸 수 없는 구조는 그대로였습니다.
- **딥링크는 앱만으로 완성되지 않습니다.** 메모·문자에서는 열리던 링크가 카카오톡에서는 웹으로만 열렸고, 웹 페이지가 앱을 직접 깨워야 해결됐습니다. 모집글 링크에서 같은 문제가 한 번 더 생긴 뒤로는, 새 링크 경로를 열 때 앱 수신·OS 연결 파일·웹 브릿지를 한 작업으로 보고 웹 저장소에 짝 이슈를 함께 냅니다.
- **보안 대책은 막을 위협의 범위부터 정해야 합니다.** QR 만료는 찍어 둔 사진의 재사용만 막고, 위조 QR이나 기기 시계 조작은 막지 못합니다. 막아야 할 것이 사진 재사용이라고 범위를 먼저 정하니, 서버 서명까지는 필요 없다고 판단할 수 있었습니다.
